# 保真度契约（权威源）

本文件是 `lofi-prototype` 保真度、覆盖面和停止规则的**唯一权威表述**。`SKILL.md` 只放摘要，冲突时以本文件为准。

## 1. 为什么需要一份成文的保真度契约

不写下来的话，agent 有两种稳定的跑偏方式：

- **往上跑偏**：不知不觉画成高保真——加渐变、加阴影、挑字体、配色。结果是评审人开始讨论"这个蓝色不太对"，而信息架构和任务流的问题一个都没被发现。
- **往下跑偏**：画成一堆灰盒子，看不出这屏是干什么的、主操作是哪个、失败了怎么办。走查不出任何东西。

契约要同时挡住这两头：**结构清楚到能走查，视觉素到没人想讨论视觉。**

## 2. 输入契约

按优先级读，缺的不要自己补齐：

1. **当前 task 的 `prd.md`** —— 这一片的屏 / 交互序列清单、必须表达的状态、明确不做的部分、会影响交互的技术限制、标了待确认的项。**这是范围的唯一来源**。
2. **`docs/discovery/wireframe/*/final/` 下已定稿的屏或交互序列**（有 UI 是 `final/index.html`，非 UI 是 `final/interaction-sketch.md`）—— 同类屏 / 同类序列要沿用既有模式，见 §4.1。逐片推进时这一步不能省。
3. `docs/discovery/brief.md`（存在时）—— 只取「措辞」一节按它用词，以及「阶段目标」用来判断本片是否偏离。**不从这里取范围**：简报是产品级的，范围是切片级的。
4. 目标仓库既有产品的截图、页面或设计规范（给存量产品加功能时，信息架构要跟现状对齐）
5. 目标仓库 `AGENTS.md` 的文档路径约定

**缺信息时不要静默补默认值**，在产物里显式标记：

- `[假设]` —— 我按某个合理默认画了，需要确认
- `[待确认]` —— 简报没说，也没法合理默认
- `[设计决策]` —— 我在两种合理做法里选了一种，理由是什么

这三个标记要在原型界面上**可见**（不是只写在注释里），走查时才会被看到。

## 3. 保真度红线

### 3.1 视觉（往上跑偏的闸）

- **只用灰阶**，加**一个**中性强调色，且强调色**只用来标出该屏的主操作**。不用它做装饰、分区或状态色。
- 状态用**文字标签 + 边框**表达（`失败`、`执行中`、`无权限`），不用色彩语义（不做红绿黄）。理由：色彩语义是视觉阶段的事，提前定会被当成已定稿。
- **禁止**：渐变、阴影、圆角以外的装饰、插画、品牌 logo、真实头像、装饰性动画、hero 区块。
- **不挑字体**：用 `system-ui` 系统栈。不定最终字号阶梯和间距体系。
- 图用占位框 + 文字说明（`[图表：近 7 天同步成功率]`），不画真图表。
- 图标用纯文字或极简内联 SVG，**不引图标库**。

### 3.2 内容（往下跑偏的闸）

- 文案要**真实到能判断信息层级**：写「同步任务列表」不写「标题」；写「连接测试失败：认证被拒绝」不写「错误提示」。
- 列表要有**几行像样的假数据**（3–5 行），能看出列宽和信息密度。全是 `Lorem ipsum` 或 `xxx` 的原型走查不出东西。
- 每屏**必须有一个明确的主操作**，且用强调色标出。看不出主操作的屏说明信息架构没想清楚。
- 屏之间的**返回、取消、异常恢复路径必须明确**——这是原型比文档强的核心地方，别省。

### 3.3 技术（保证产物可用）

- **自包含单文件**：CSS 和 JS 全内联。**零外部请求**——无 CDN、无 npm 包、无外链字体、无远程图片。
  理由：需要联网或构建的原型不能 git 提交对比、不能离线双击打开、下一个 session 也不能直接改。
- 用原生 HTML + 少量原生 JS。不引框架。
- 屏切换用 `location.hash`，保证每屏有可分享的地址。
- **不写进 `src/`**、不接真实接口、不生成生产级前端代码。原型是丢弃品。

### 3.4 范围

- **不引入本片范围外的功能**。想加的先在产物里标 `[假设]` 或直接问，不静默添加。
- `prd.md` 里「明确不做」列的，一律不画。
- **切片不能在原型里静默长大**。发现本片其实需要更多屏时，要么说清楚并让人确认扩片，要么挪进 `brief.md` 的切片清单当后面的片。

## 4. 覆盖面契约

**覆盖面 = 当前切片声明的全量**，不是本片主链路，也不是整个产品。

不变量：

```
原型覆盖面 ≥ 本片实现覆盖面  → 有据可依
原型覆盖面 < 本片实现覆盖面  → 缺口由 AI 自由发挥补上（正是要防的事）
```

注意这个不变量锚的是**你即将实现的东西**，不是产品愿景。逐片推进时它照样成立，成本却低一个量级——所以**不要**为了"完整"去画后面几片的屏，那些屏的需求还没被 brainstorm 收敛过，画了也是猜。

本片的三类都要画全，后两类最常被漏：

| 分组 | 内容 | 漏了会怎样 |
|---|---|---|
| 主链路 | 入口 → 关键操作 → 成功结果 | 一般不会漏 |
| **支撑屏** | 本片涉及的详情、编辑、删除确认 | 实现时这些页面变成 AI 现编，「编辑复用向导」之类的真实约束丢失 |
| **异常态** | 校验冲突、连接失败、无权限、部分成功 | 最贵的一类。这些在文档里一句话，在实现时是三天 |

### 4.1 沿用既有结构（逐片推进的一致性保障）

**出方案前必须读 `docs/discovery/wireframe/*/final/` 下所有已定稿的屏或交互序列。**

逐片推进唯一丢掉的东西是跨片一致性：第一片的列表页和第三片的列表页可能长得完全不一样，而没有任何一处机制会发现。这一步是唯一补救：

- **同类屏沿用既有模式**——同样的筛选位置、行操作位置、空态表达。
- **非 UI 同类序列同理**——子命令分组方式、错误往 stdout 还是 stderr、退出码编号、`--json` 给不给、幂等语义，定过一次就沿用。
- **结构性偏离写进取舍说明**，让人有机会否掉。静默偏离是本 skill 在逐片模式下最主要的失败形态。
- 这是第一片（没有既有定稿）→ 跳过，但要意识到**本片定下的模式会被后面所有片沿用**。

**两个分支的定稿都在 `*/final/` 下**（`final/index.html` 与 `final/interaction-sketch.md`），见 §7。这个布局是硬要求而不是习惯：本节的检查只扫 `*/final/`，非 UI 定稿一旦落在别处，本节对非 UI 分支就等于不存在——而那正是最容易漏的一类契约（退出码、错误格式、幂等语义都不在界面上，没人会凭印象发现它们跨片不一致）。

### 必须能点着看的状态

每个声明状态都要能通过 devbar 切过去，不能只写在注释里：

- 空（还没有任何数据）
- 加载中
- 操作失败（不同失败原因给不同下一步，不要一个"出错了"糊过去）
- 无权限（该角色看到的是什么，而不是一个报错页）
- `prd.md` 里列的其他状态

## 5. 方案契约

- **2–3 个方案**，每个都覆盖本片全量屏/序列。不是"A 画主链路、B 画异常"。
- **必须有结构性区分度**，区别落在信息架构与任务流组织：任务流形态（向导/长表单/内联渐进）、信息组织（按对象/按阶段/单工作台）、配置与执行的关系、异常处理位置。
- 三套雷同皮肤换色**不算**方案——要看的东西翻三倍而信息不翻倍。
- 每案先给**一句话取舍说明**（牺牲什么换什么），再给屏。让人在读屏之前就能筛方向。
- 2 个方案够用时不必凑 3 个。

## 6. 停止规则

| 项 | 上限 | 超了怎么办 |
|---|---|---|
| 走查轮次 | **2 轮** | 剩余分歧记「待确认」或「挪到后面的切片」，不进第 3 轮 |
| 选案 | **一次定** | 落选方案想保留的要素当场合并进定稿；不留"再看看" |
| 本片屏 / 序列数 | > 6 触发**警报** | 提醒「这一片是不是切大了」，回 `brief.md` 的切片清单看要不要拆，结论留痕。警报要求确认，**不阻塞** |
| 问题记录字段 | 4 个 | 不套 `design-review` 的 8 字段台账（见下） |

**收敛压力放在轮次与拍板上，不放在覆盖面上。** 无限审计的形态是"反复评审同一份东西、停不下来"，不是"一次把这一片画得全"。所以本片画全是对的，反复摇摆是错的。

**6 屏这个阈值是切片粒度的信号，不是画图预算。** 一片超过 6 屏，通常说明它不是一个能独立端到端验证的切片，而是几个切片被打包了。修法是回去拆片，不是压缩原型。

**为什么不套完整台账**：`design-review` 的八字段证据格式（`id` / `category` / `severity` / `evidence` / `trigger` / `impact` / `affected_requirement` / `blocking_reason`；进台账还要再加 `status` 与 `reopen_condition`）是为设计准入设计的，需要可定位的设计依据。原型走查阶段的发现形态是"这步太绕""失败了不知道干什么"——套八字段等于要求用户为每条直觉反馈写举证材料，会直接把走查变成新的审计负担。四字段（现象/判定/动作/落点）够用。

## 7. 输出契约

每一片一个目录，目录名 = task slug：

```
docs/discovery/wireframe/
├── <task-slug-1>/                   # 有 UI 的片
│   ├── 方案A/index.html
│   ├── 方案B/index.html
│   ├── final/index.html             # 本片定稿
│   └── walkthrough-notes.md         # 本片走查发现 + 选案留痕
├── <task-slug-2>/                   # 非 UI 的片
│   ├── interaction-sketch.md        # 全部方案（含落选），供回看
│   ├── final/interaction-sketch.md  # 本片定稿：只含选中方案
│   └── walkthrough-notes.md
└── …
```

三条硬要求：

- **`final/` 是固定子路径，两个分支都用它**。后面的片要靠它做一致性沿用（§4.1），而那条检查只扫 `*/final/`——非 UI 定稿落在别处就等于没有一致性保障。
- **`final/` 里只放选中方案**。放全部方案的话，下一片读的时候不知道该沿用哪个，等于没定稿。
- **目录名用 task slug**，不用方案名或日期。它是「这片原型属于哪个 task」的唯一线索。

**回写 `prd.md`** 是输出的一部分，不是可选项。走查暴露的东西不回到当前 task 的 `prd.md`，实现时读的就还是走查之前的旧共识。本 skill **不置任何 approved 标记**——批准发生在 brainstorm 的 planning summary 那一步，由用户做。

## 8. 生命周期（权威源）

原型是**开工前的丢弃品**：不进 `src/`、不是实现起点、**不是** UI 视觉验收基准（那是视觉阶段的 `design-system/prototype.html`，阶段、保真度、目的都不同，名字也不同）。

维护责任按片划分，这是唯一权威表述——其他文件只引用本节，不各自另写一套：

### 这一片还没实现完：两者同步

**涉及结构或流程的变更，两者同步**：当前 task 的 `prd.md` ↔ `wireframe/<task-slug>/final/`。

- 只改一处就是漂移。两者不一致时，下一个 session 不知道该信哪个。
- 只影响字段、规则、文案的变更**不需要**动原型——原型只表达结构与流程。判据：这次变更会不会增删屏、改变流转顺序、或改变异常恢复路径？不会就只改 `prd.md`。
- 逐片模式下同步对象只有两个（旧版是三个，因为那时简报里还有全量屏清单）。简报不再持有屏信息，所以它不在同步链里。

### 这一片实现完了：留着，不回溯维护

`wireframe/<task-slug>/final/` **保留**，因为后面的片要靠它做一致性沿用（§4.1）。但它**冻结**：不随后续改动更新，也不是任何实现的验收基准。它记录的是「这一片当初是按什么结构定的」。

想知道某个界面现在实际长什么样，看代码，不看原型。

### 落选方案

保留在 git 里供回看，但不再是任何东西的源真。有 UI 的片是 `方案A/` `方案B/` 目录，非 UI 的片是 `interaction-sketch.md` 里的落选段落——两者都可以删，历史由 Git 保存。**不能删的是 `final/`**，后面的片要读它。

### 和视觉稿的关系

**视觉稿**（Figma / 高保真 HTML / 截图）是另一回事：它不随需求文档维护，也不是任何东西的结构源真。

低保真骨架的定位不同也更精确：它**不进实现规格本体、不随每次编辑更新**（改个字段校验不用动原型），但在这一片实现完之前，**结构性变更必须与 `prd.md` 同步**。两条不冲突——一条说"不是规格的一部分"，一条说"这一片做完之前要保持一致"。

`design-system/prototype.html`（视觉验收基准）与 `wireframe/`（结构依据）名字、阶段、目的都不同，**不要合并**，也不互为源真。
