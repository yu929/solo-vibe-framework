# Lofi Prototype · 完整手册

`SKILL.md` 是执行入口，保真度和停止规则的权威源是 [`fidelity-contract.md`](fidelity-contract.md)。本文件放操作细则、判据和对照例。

## 1. 这一步在解决什么

`prd.md` 写完就开工，结构错了要到实现阶段才发现，而那时代码已经成型。

调整后是「planning 写完 `prd.md` → 低保真原型 → 走查拍板 → 才 `task.py start`」。核心理由：

> **产品想法主要在脑子里成形的人，通过界面和流程发现问题远比通过长篇文档容易。**

所以原型不是实现的下游装饰，而是**本片实现的结构依据**。这决定了两件事：

1. 覆盖面必须等于**这一片**声明的全量（不能只画主链路，也不需要画后面几片）；
2. 走查结论必须回写 `prd.md`，否则实现时读的是旧共识。

**为什么不画整个产品**：不变量是「原型覆盖面 ≥ 实现覆盖面」，它锚的是**你即将实现的东西**。后面几片的需求还没被 brainstorm 收敛过，现在画等于替它们猜——那是把没验证过的结构写死，正是这套流程要防的事。

## 2. 和视觉设计阶段的分界（最容易搞混的一处）

| | 本 skill（planning 期） | `ui-ux-pro-max`（视觉阶段） |
|---|---|---|
| 时机 | `task.py start` **之前** | 结构定了之后 |
| 管什么 | **结构与流程**：有哪些屏、信息怎么组织、任务怎么流转、异常怎么恢复 | **视觉**：配色、字体、间距、组件、设计系统 |
| 保真度 | 灰阶骨架，素到没人想讨论视觉 | 高保真，就是要定视觉 |
| 产物 | `docs/discovery/wireframe/<task-slug>/` | `design-system/MASTER.md` + `design-system/prototype.html` |
| 角色 | 本片实现的结构依据 | UI 视觉验收基准 |
| 覆盖面 | **当前切片**全量屏 / 交互序列 | 随切片增量 |

**不要把两者互相升级或替代。** 本 skill 的产物不是视觉验收基准；视觉阶段的 `prototype.html` 也不能反过来当需求依据。两个文件名字不同不是偶然，是为了让人一眼看出它们不是一回事。

另有一条相关纪律：「别前置写全部页面的**文字规格**——那是 UI 版的无限审计」。逐片模式天然遵守它：本 skill 每次只画一片，且画的是**你验得了的东西**（点着走的屏）；那条禁的是**你验不了的东西**（大段页面文字规格）。

## 3. 方案怎么分化

**要求**：2–3 个方案，每个覆盖本片全量屏 / 交互序列，且必须有**结构性区分度**。

分化维度（挑 1–2 个维度分化，不要全维度乱排列组合）：

| 维度 | 方案 A 侧 | 方案 B 侧 |
|---|---|---|
| 任务流形态 | 分步向导（步骤清晰，改配置要重走） | 单页长表单（一屏看全，首次信息量大） |
| 信息组织 | 按对象分组（任务 / 映射 / 记录各一屏） | 按流程阶段分组（配置 → 执行 → 结果） |
| 配置与执行 | 拆两屏（配置完再单独触发） | 合一屏（配置即预览即执行） |
| 异常处理位置 | 阻断式弹窗（错了走不下去） | 内联提示 + 允许继续（最后统一校验） |
| 密度 | 列表 + 详情抽屉 | 单一工作台（主从布局） |

**不算方案的**：

- 三套一样的结构换个强调色或圆角
- A 画主链路、B 画异常（那是一个方案拆成两半）
- 只在按钮位置、文案措辞上不同

**判据**：把两个方案的屏清单并排放，如果屏的数量、名字、分组基本一致，那它们是同一个方案。

**取舍说明先行**：每案先给一句话「牺牲什么换什么」，让人在读屏之前就能筛掉明显不对的方向。这一步能省掉大量走查时间。**沿用还是偏离既有结构，也写在这句里**（见 §3.1）。

**2 个够用时不必凑 3 个。** 方案数不是目标，选出对的那个才是。

### 3.1 分化的边界：不要在已定结构上分化

逐片推进时，方案分化只应发生在**这一片新引入的结构**上。

前面的片已经定了「列表 + 详情抽屉」，这一片就不要拿「列表 + 详情页」当作一个方案 —— 那不是在给这一片选结构，是在推翻上一片，代价是已经实现的代码。

判据：**这个差异点，前面的片定过吗？**

- 定过 → 沿用，不作为分化维度。真觉得当初定错了，那是一次独立的重构决策，走 finding 流程，不夹带在本片的选案里。
- 没定过 → 可以作为分化维度，而且**这一片定下的会被后面所有片沿用**，值得多想一轮。

## 4. 走查怎么做

### 走查前

告诉用户具体怎么操作：

```
直接在浏览器打开（不需要装任何东西、不需要联网）：
  docs/discovery/wireframe/<task-slug>/方案A/index.html
  docs/discovery/wireframe/<task-slug>/方案B/index.html

顶部工具条：左边切屏，右边切状态（正常/空/加载中/错误/无权限）。
建议顺序：先按本片主链路从入口点到成功结果，再逐个切异常态。
```

**非 UI 的片没有浏览器这一步**，走查对象是 `docs/discovery/wireframe/<task-slug>/interaction-sketch.md`：按方案逐段读，顺序同样是「主链路 → 辅助命令 → 异常路径 → 状态迁移」。引导语要换成让人**照着敲一遍**——「你现在要跑一次同步，照方案 A 的序列念一遍你会敲什么」。屏能让人一眼看出别扭，命令序列不会，得靠这一步逼出来。

### 走查中

- **接收大白话**："这步太绕""这两个应该在一屏""失败了不知道该干什么""这个列表少了我要的列"。原样记进 walkthrough-notes 的「现象」列，**不要翻译成术语**——翻译会丢信息。
- **当面问待确认项**。`prd.md` 里标了待确认的那些，此刻对着屏问，答案通常立刻就有。这是原型的隐性价值：抽象问答不出来的问题，指着屏就答得出。
- **主动追问被跳过的状态**。用户通常只走主链路。要主动引导："切到「无权限」看一下，审计员进来看到这个对吗？"异常态是最贵的一类，也是最容易在走查时被跳过的。
- **留意术语分歧**。用户指着屏说的词和简报「措辞」一节不一致时，当场问清是哪个意思，裁决结果回写简报。走查是术语第二次被检验的时刻。
- **留意范围溢出**。用户说"顺便把 X 也加上"时，先问这是不是这一片的事。多数情况它属于后面的片——记进 `brief.md` 的切片清单，不在这一片长大。

### 走查后

按 `assets/walkthrough-notes-template.md` 记录，每条四字段：现象 / 判定 / 动作 / 落点。

判定只有四个取值：

| 判定 | 什么时候用 |
|---|---|
| **改 prd** | 这一片的需求要变（流程、状态、规则） |
| **改原型** | 需求没变，只是结构或表达不对 |
| **挪到后面的切片** | 这事该做，但不是这一片 |
| **待确认** | 需要别人拍板或需要更多信息 |

**「落点」必须是具体位置**（`prd.md` 某节 / 某屏 / `brief.md` 切片清单第几行）。写「已知悉」等于没记。

## 5. 选案与停止

**方案一次定**。走查后选定 1 个；落选方案里想保留的要素**当场合并**进定稿并记录，不留"再看看"。

> 在方案之间反复摇摆是本阶段唯一真会失控的地方——不是画得多。

这一点值得说透：无限审计的形态是「反复评审同一份东西、问题越修越多、停不下来」。把这一片画全**不是**无限审计，它是一次有限的、有明确终点的工作。真正会无限化的是「A 好像更清楚，但 B 那样更紧凑，要不再看看 C」——所以纪律必须落在选案上。

**走查最多 2 轮**。第 2 轮之后仍有分歧的，判定写「待确认」或「挪到后面的切片」，进回写，不进第 3 轮。

**单片规模警报（不阻塞）**：本片屏数 / 交互序列 > 6 时提醒一次「这一片是不是切大了」，回 `brief.md` 的切片清单看要不要拆，结论留痕。

这个阈值是**切片粒度的信号，不是画图预算**。一片超过 6 屏，通常说明它不是一个能独立端到端验证的切片，而是几片被打包了。修法是回去拆片，不是压缩原型。

## 6. 回写怎么写

回写不是可选项。走查暴露的东西不回到当前 task 的 `prd.md`，实现时读的就还是走查之前的旧共识——那这一整步等于白做。

常见回写项：

| 走查发现 | 回写到 |
|---|---|
| 漏了支撑屏 / 异常态 | 本片 `prd.md` 的屏清单增补 |
| 某状态其实不需要 | 本片 `prd.md`「必须表达的状态」删除 |
| 流转顺序不对 | 本片 `prd.md` 的流程描述 |
| 走查中定掉的待确认 | 本片 `prd.md` 划掉 |
| 走查中新暴露的问题 | 本片 `prd.md` 补上，标决策人和期限 |
| **这事该做但不是这一片** | `brief.md` 的切片清单加一行，**不在本片实现** |
| **这一片其实不该这么切** | `brief.md` 的切片清单重排，说明理由 |
| 某个词一直被两种意思混用 | `brief.md` 的措辞一节裁决并补上 |
| 阶段目标被证伪 | `brief.md` 的阶段目标，并说明——这比实现后发现便宜两个量级 |
| 定稿方案路径与改动摘要 | 本片 `prd.md` + `walkthrough-notes.md` |

回写完把材料交给 brainstorm 的 planning summary，由**用户**在那里批准 `task.py start`。

> **本 skill 不置任何 approved 标记。** 批准这件事已经由 Trellis 的 planning 门禁拥有了（"没有用户显式批准 planning summary 就不许 `task.py start`"），再加一个标记就是同一事实两处维护。

## 7. FAQ

**Q：为什么不把整个产品的屏一次画全？**
因为不变量锚的是**你即将实现的东西**：`原型覆盖面 ≥ 实现覆盖面`。逐片推进时，这一片只实现这一片，所以只需覆盖这一片。

后面几片的需求还没被 brainstorm 收敛过，现在画等于替它们猜结构——而猜出来的结构一旦画成 HTML 就会被当成已定稿，下一片的 planning 会绕着它走。**没验证过的结构不要写死**，这是整套流程的第一原则。

**Q：那不会每片各画各的、最后拼不起来吗？**
这是逐片模式唯一真实的代价，所以有 §3.1 和 `fidelity-contract.md` §4.1 两条硬纪律：出方案前必须先读所有已定稿的 `*/final/`，同类屏沿用既有模式，偏离要在取舍说明里写明理由。

这条不能省。省掉它，逐片模式就退化成"每片重新发明一次列表页"。

**Q：为什么这一片不能只画主链路？**
因为实现的时候会做全。原型覆盖面小于本片实现覆盖面，缺口就由 AI 自由发挥补上——那正是这套流程要防的事。支撑屏和异常态尤其不能漏，它们在文档里是一句话、在实现时是三天。

**Q：能不能直接出高保真，反正都要画？**
不能。高保真会把走查的注意力吸到视觉上（"这个蓝色不太对"），而信息架构和任务流的问题一个都不会被发现。保真度红线的存在就是为了让人**没东西可讨论**，只能讨论结构。

**Q：用 wired-elements 之类的手绘风组件库不是更"低保真"？**
手绘风确实能压低视觉讨论，但它需要 CDN 或 npm。需要联网或构建的原型不能 git 提交对比、不能离线双击打开、下一个 session 也不能直接改。灰阶 + 零依赖能达到同样的效果，代价更低。

**Q：原型要不要接真实数据/接口？**
不要。原型是丢弃品，不进 `src/`。假数据要像样（3–5 行真实感文案）就够了。

**Q：走查完发现方案都不对怎么办？**
分两种，判据是「不对」的层级：

- **这一片的结构不对** → 回 `prd.md` 重新收敛这一片要做什么，再出方案。
- **这一片就不该这么切**（比如它根本没法独立端到端跑通）→ 回 `brief.md` 的切片清单重排，说明理由。

两种都算一次成功的走查——它在 `task.py start` 之前拦住了错误，这正是它存在的理由。

**Q：走查发现这一片需要的屏比 prd 里写的多怎么办？**
先判断多出来的是**本片必需**还是**顺手想加的**：

- 本片必需（比如少了它主链路就断了）→ 补进 `prd.md`，本片画。
- 顺手想加 → 记进 `brief.md` 的切片清单当后面的片。

**切片不能在原型里静默长大。** 这是逐片模式最主要的失控形态：每片都"顺手多做一点"，三片之后就回到了一次做全。

**Q：定稿之后还能改吗？**
能。规则见 [`fidelity-contract.md` §8 生命周期](fidelity-contract.md)（权威源），要点：这一片实现完之前，**结构或流程**的变更要让 `prd.md` 和 `wireframe/<task-slug>/final/` 两者同步；只改字段、规则、文案的变更不用动原型。这一片实现完之后 `final/` 冻结——保留供后面的片沿用结构，但不回溯维护，想知道界面现在实际长什么样就看代码。

**Q：这一步要花多久？**
一片 3–5 屏，2–3 个方案的灰阶骨架通常是一次对话的量。走查 1–2 轮。总成本远低于它省下的返工——在原型上挪一屏是几分钟，在实现后挪一屏是几小时，在上线后挪一屏是几天。

**Q：每一片都要走一遍吗？**
不。只有**有交互面变更**的片要走。纯后端重构、纯配置调整、只改一条规则的片直接继续 planning。判据在 `SKILL.md` 的输入门禁第 3 条。
