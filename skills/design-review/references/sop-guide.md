# 设计准入评审完整手册

> 收敛纪律的权威源是 [`review-adjudication.md`](review-adjudication.md)。本手册只解释**操作层**：台账怎么维护、什么时候升级多 agent、怎么判断收益递减。纪律条文不在这里复制。

## 1. 为什么开放式评审会发散

把"审到没有新问题"当目标，通常永远到不了：

1. 不同 session 的注意力采样不同；
2. reviewer 会带入不同用户量、可靠性和安全假设；
3. "找问题"这个提示天然会累积假阳性；
4. 大多数设计不能只靠文档获得完备证明——很多问题必须靠类型、测试、垂直切片和实际运行才能证伪。

结论：看**新增问题的严重度、是否存在不可逆风险、主流程能否实施验证**，而不是看"还能不能找出意见"。

## 2. 问题台账怎么维护

路径由目标仓库或调用方决定，模板用 [`../assets/review-ledger-template.md`](../assets/review-ledger-template.md)。

- **每轮先读完整台账**。
- `REJECTED_OUT_OF_SCOPE`、`REJECTED_UNSUPPORTED`、`DEFERRED`、`ACCEPTED_RISK` 未满足 `reopen_condition` 不得重提。
- **只有和旧台账对比过，才能把一个发现称为"新"的。**

状态含义：

| status | 含义 |
|---|---|
| `ACCEPTED_BLOCKING` | P0/P1，阻塞开工 |
| `ACCEPTED_NON_BLOCKING` | P2，进入 backlog |
| `DEFERRED` | 延后决定，**必须有客观 `reopen_condition`** |
| `ACCEPTED_RISK` | 知情接受，记录理由 |
| `DUPLICATE` | 与既有 id 重复 |
| `REJECTED_OUT_OF_SCOPE` | 超出当前范围 |
| `REJECTED_UNSUPPORTED` | 无证据或无触发路径 |
| `CLOSED` | 修复已落地，或 reopen 条件已兑现并完成处置 |

`reopen_condition` 必须**可判定**："需求新增跨区域容灾""实测并发可突破业务不变量"都行，"以后再看"不行——不可判定的条件等于永久关闭。

关闭条目时记录 `resolution`，说明哪份文档或哪段实现完成了处置。

## 3. 什么时候升级多 agent

**默认单 agent 单趟完成两轮并承担裁决。**

只有这些范围才值得升级独立 reviewer：鉴权、数据迁移、不可逆操作、涉钱、跨系统一致性。

升级后三件事**不变**：评审预算（仍是两轮）、证据门槛、**唯一裁决点**。多 reviewer 只提高召回，不改变裁决方式——发现先合并去重，不取并集全改，不用多数投票定真假。

## 4. 设计海拔对照

设计只锁承重决策，其余下放编码与测试：

| 现在必须定 | 下放编码期 |
|---|---|
| 数据所有权与权限模型 | 内部类结构与辅助模块 |
| 关键模型、关系和约束形状 | 大部分设计模式和通用化程度 |
| 信任边界、授权原则、凭据边界 | 锁、CAS、重试的具体实现 |
| 外部边界与长期契约形状 | 索引细化和非瓶颈优化 |
| 一致性要求 | 普通算法和局部分支 |
| 迁移、删除与兼容策略 | 次要异常文案 |

对照例：

- ✅ 好：「同一业务身份同时只能有一个生效对象」——可验证的不变量。
- ❌ 太低：在设计里写死具体锁 key、CAS 语句和退避曲线。应写「编码期选择实现，并用并发测试证明该不变量」。
- ✅ 好：「外部契约不承载凭据值，错误响应只返回稳定错误码」——边界和验收依据。
- ❌ 太低：提前设计一个没有消费者的通用事件总线或插件框架。

## 5. 轨 overlay

本 skill 的 reviewer 是**轨无关骨架**。轨硬约束由目标仓库提供 overlay，主 agent 加载后一并交给 reviewer。

- overlay 的内容是该轨的不变量：数据隔离机制、数据访问路径约定、凭据处理规则、构建与迁移约定。
- **轨专属规则没有目标仓库证据时不得启用**，更不能跨轨外溢。
- 没有 overlay 也能跑，但报告里要注明"未加载轨 overlay"，让人知道覆盖面是通用的。

## 6. 与其他环节的关系

| 环节 | 谁负责 | 本 skill 的边界 |
|---|---|---|
| 需求完整性 | 产品简报 + `lofi-prototype` | **不补需求、不做需求评审** |
| 单个 task 的实现正确性 | Trellis 的 check 阶段 | 不审实现代码 |
| 通用代码正确性 | 通用代码评审工具 | 同上 |
| 轨不变量 | 目标仓库的评审清单 | 同上 |
| 编码期发现（finding） | 见纪律权威源的「编码期发现」节 | 本 skill 不处理 finding 升级 |

**第三、第四轮纯文档评审，通常不如做一个垂直切片有价值。**

## 7. FAQ

**Q：换个 agent 还是会有新意见，机制失效了吗？**
没有。本机制控制的是"哪些新意见**足以阻塞**"，不是消除新意见出现的概率。有新意见很正常，问题是它们能不能过证据门槛。

**Q：范围外的问题怎么处理？**
裁决为 `REJECTED_OUT_OF_SCOPE`，并写清重新打开条件。不要因为"顺手也能改"就纳入——那正是范围失控的起点。

**Q：P1 一定要修改吗？**
不一定，但必须**明确选择**：修复、推迟（带 `reopen_condition`）或接受风险（记录理由）。没有选择就是没处置。

**Q：什么时候该重做一次全面设计？**
只有承重假设被需求变化或实现证据证伪时。**不能因为又出现了偏好意见就重启评审**——那是无限审计的复发。

**Q：台账要不要提交进 git？**
要。它是跨 session 记忆，不提交等于每个新 session 从零开始。发布时按 §2 迁移开放项后再删。
