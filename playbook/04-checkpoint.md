## 什么时候用这个场景

**触发判据（满足任一条）**：

- 阶段目标达成了
- 连续做完了 **3–5 个切片**
- 准备发一个版本
- 产品目标本身变了
- **架构开始阻碍开发**（连着两片都在绕同一个东西）
- 文档和代码明显对不上了

## 为什么需要这一篇

**Trellis 没有这一层，而逐片推进特别需要它。**

Trellis 的 `finish-work` 看起来像收尾，其实只有四步：查状态 → 检查 git 干不干净 → `task.py archive` → 写 journal。零个产品问题，而且只管当前这一个 task。`trellis-update-spec` 也是 task 级的——它把这一片的经验升级进 `.trellis/spec/`。

所以跑五十个 task 之后，你手上有：

```
.trellis/spec/       一堆编码规范
.trellis/tasks/archive/   一堆已归档的单次改动
.trellis/workspace/  一条时间流水
```

**没有任何一处回答「这个产品现在整体是什么」。**

这本来是「一次画全 MVP」在帮你兜的事——画的时候你被迫看了一遍全貌。改成逐片之后那个动作没了，如果不补一个定期回头看，就是净变差。这一篇是那个补丁。

## 开始之前

- [ ] 手上没有进行中的 task（有就先 Finish，别在半截上盘点）
- [ ] `docs/discovery/slices.md` 还在

## 步骤

### 步骤 1 · 让 AI 先摊开现状

**我敲什么**：

```
做一次项目检查点。先只做汇总，不要给建议：
1. 列出 .trellis/tasks/archive/ 里已完成的切片，每个一句话
2. 对照 docs/discovery/slices.md §4 的切片清单，标出：做了但不在清单里的、清单里还没做的
3. 列出 .trellis/spec/ 里最近新增的约定
4. 如果有 docs/discovery/decisions.md，把写了「什么时候回来重看」的条目列出来，
   逐条说触发条件到了没有（到没到就是事实判断，不要给建议）
5. 不要下结论
```

**AI 会产出什么**：一张现状表。

**为什么要求「不要给建议」**：让它同时汇总和判断，它会把汇总裁剪成支持自己判断的样子。分两步，第一步的产物你才敢信。

**怎么确认这步成了**：你看着那张表，能想起每一片当时在干什么。

### 步骤 2 · 七个问题

一个一个过。**这是给你自己回答的，不是给 AI 回答的**——AI 可以帮你找证据，但答案得你来定。

| # | 问题 | 答"不"的时候做什么 |
|---|---|---|
| 1 | **当前阶段目标还成立吗？** | 改简报 §2，说明为什么变 |
| 2 | **已完成的切片加起来，构成一件用户能完整做成的事了吗？** | 找出断在哪一环，那就是下一片 |
| 3 | **有没有无意识扩张？**（做了但不在 §4 清单里的） | 每条问一遍：当初该做吗？该，补进 §3 能力地图；不该，记下来别再犯 |
| 4 | **架构和交互还一致吗？** | 不一致的地方记 finding，不要顺手改。**但先分清是哪一层**——见下 |
| 5 | **测试覆盖到当前核心路径了吗？** | 补测试，那是下一片的一部分 |
| 6 | **有没有该删掉而不是继续实现的需求？** | 移进简报 §3「明确不做」，写原因 |
| 7 | **能不能发一个稳定版本了？** | 说得出还差什么，就是下一片 |

**第 3 问和第 6 问最值钱。** 前者抓的是逐片模式最容易积累的病（每片顺手多做一点），后者是唯一一个会让工作量**变少**的问题——而它几乎总是被跳过。

**第 4 问答"不"时，先分清不一致出在哪一层**：

- **某一片实现跑偏了** → 记 finding，当下一片的候选。这是常态。
- **承重决策本身不成立了**（数据归属、权限边界、模块切分、长期契约）→ 这不是记一条 finding 能解决的，打一次 `/design-review`（见 [`README.md`](README.md)「一个不在主流程里的出口」）。

判据：修它要不要动**已经做完的好几片**？要，就是承重层。

承重决策通常在 `docs/discovery/decisions.md` 里有条目——**先去读当初的「为什么」再判断**。很多"架构不对"其实是当初的取舍换了前提（那时只有你一个人用、那时没有第二个数据源），前提变了就推翻，在 decisions.md 里**新写一条**说明推翻了哪条，别改旧条目。

这也正好对上本篇的触发判据「架构开始阻碍开发（连着两片都在绕同一个东西）」——**连着两片绕同一个东西，通常就是承重决策的问题**，不是那两片各自没做好。

### 步骤 3 · 回写简报

检查点唯一的产物是**更新后的 `docs/discovery/slices.md`**：

- §2 阶段目标——达成了就写下一阶段的，变了就改
- §3 能力地图——扩张的补进来，该砍的移进「明确不做」
- §4 切片清单——做完的划掉，新识别的加上并排依赖
- 变更历史加一行

**不新建文件。** 不建 checkpoint 报告、不建 review 记录、不建状态字段。检查点是一个动作，不是一份产物——它的结论必须落进那份一直被读的文件，落进别处就等于没落。

## 我该在哪停下来看

| # | 拍什么 | 为什么 |
|---|---|---|
| 1 | **阶段目标还成立吗** | 这是整个检查点的意义。答"是"就一分钟结束，答"否"才是它值回票价的时候 |
| 2 | **哪些该砍** | 唯一让工作量变少的问题，也是最容易跳过的 |
| 3 | **下一阶段目标是什么** | 不定下来，下一批切片又会变成一批孤立功能 |

## 常见卡点

### 「每次都答『还成立』，感觉在走过场」

那就把频率调低（5 片一次而不是 3 片），但**别取消**。

而且注意：第 1 问答"是"是常态，不是走过场。这七问里真正会抓到东西的通常是第 3、4、6 —— 扩张、不一致、该砍的。第 1 问是个便宜的兜底。

### 「AI 直接给了一堆改进建议」

打断，让它先只做汇总。见步骤 1。

一份没有判断的现状表，你自己看两分钟就有结论，而且那个结论是你的。AI 给的建议清单读起来更专业，但你没法验证它是不是把汇总裁剪成了支持结论的样子。

### 「发现前面某一片做错了」

**不要顺手改。** 记 finding（4 字段：现象 / 证据 / 该改哪个 spec / 状态），当成下一片的候选。

检查点是**盘点**，不是施工。在检查点里开始改代码，它就会变成一次没有边界的重构——那正是这套流程要防的事。

### 「简报和实际做出来的东西差太远，改不动了」

那就重写简报 §2 §3 §4，按**现在实际有什么**写，变更历史里记一句「本次按实际实现重写」。

简报的价值是「现在整体是什么」，不是「当初计划是什么」。当初的计划在 git 里。
