# 3 · 切片

> 把定稿拆成可以逐片交付的顺序，写进 `docs/discovery/slices.md`。
>
> 这是进 Trellis 之前的最后一步。

## 开始之前

- [ ] 完整 PRD 已收敛到字段级
- [ ] 有交互面的话，高保真已经定稿。没有定稿就开始切，第四列只能空着，实现期子 agent 也就没有结构依据

## 步骤

### 步骤 1 · 打 `/vertical-slicing`

```
/vertical-slicing
```

> 未实跑。

不要省掉这一步，也不要只把模板路径交给 AI。单独读取模板不会加载切片判据、尺度锚和阻塞边规则，最后可能只是把表格填满，却没有真正完成切片判断。

它产出 `docs/discovery/slices.md`，三节：当前阶段目标 · 切片清单 · frontier。

### 步骤 2 · 逐片验四列

切片清单有四个内容列。某一列填不出来，通常说明切法有问题：

| 列 | 内容 | 填不出来说明 |
|---|---|---|
| 切片 | 一个短标题 | —— |
| 阻塞边 | 哪几片必须先完成 | —— |
| 端到端能验证什么 | 一句话，用户视角 | 它不是切片 |
| 本片对应的高保真屏 | `design-system/screens/` 下的具体路径 | 定稿没覆盖到，或者这一片切错了 |

先用三条简单判据检查：

1. 说不出「做完这一片，用户能真正做成什么」 → 不是切片。「先把所有表建了」「先搭好框架」无法独立验证，应拆进对应的切片
2. 标题里出现「和」或「与」 → 就是两个任务，拆开
3. 一个全新 context window 装不下 → 切片太大。实现由带着全新 context 的子 agent 完成，这个窗口就是尺寸上限

阻塞边只写真正挡住当前切片的依赖。先后顺序不等于依赖；如果把排在前面的切片都写进去，整张表会被误排成串行。

### 步骤 3 · 检查第四列

第四列会直接用于填写 task 的 `implement.jsonl`。

空着的格子只有两种解释：定稿没覆盖到这一片（回 [`02-hifi.md`](02-hifi.md) 补），或者这一片切错了（重切）。

### ★ 拍板 3：切法 + 第一片是哪个

这一轮要定下切法。落选方案里值得保留的内容，当场合进最终版本。最多讨论两轮，仍有分歧就记为「待确认」，不要再开第三轮。

第一片不一定是最重要的，而应选能以最低成本证伪核心假设的那一片。它还会定下后续切片沿用的结构，例如列表样式和异常表达，因此值得多想一轮。

## 我该在哪停下来看

| # | 看什么 | 漏了会怎样 |
|---|---|---|
| 1 | 切法 + 第一片（★ 拍板 3） | 第一片定下后面都要沿用的结构 |
| 2 | 每片的第三列都填得出来 | 填不出来的那片验证不了任何东西 |
| 3 | 第四列没有空格 | 空的那片，实现期子 agent 自由发挥 |
| 4 | 阻塞边里有没有「其实不挡」的 | 整张表看起来串行，白白排掉并行的机会 |

## 常见卡点

### 「有一片映射到了十几屏」

skill 会提醒「这一片可能切太大了」，但不会阻止你继续。有些切片确实比较大，最终仍由你判断。

判据还是那条：一个全新 context window 装不装得下。装不下就拆。

### 「这次要做的是宽重构」

**不进这张表。** 改一个共享符号的类型、重命名一个到处都在用的字段，影响面铺满全仓，硬塞进纵向切片会让每一片都是红的。

走 expand–contract，见 [`06-off-path.md`](06-off-path.md)。

### 「已经有 `slices.md` 了，这次只是加一片」

只做增量，别重排整张表。见 [`06-off-path.md`](06-off-path.md)。

### 「frontier 怎么算」

frontier 指阻塞边已经全部完成、现在可以开工的切片。

按阻塞边计算，不要从表头往下数，否则会漏掉排在后面但已经可以开工的切片。每完成一片就重算一次。

### 「切片清单和 PRD 对不上」

以 PRD 为准，回去改 PRD 或改定稿，**别在切片清单里补需求**。

切片这一步只回答「多大、谁挡谁、对应哪几屏」。往切片清单里写一条缺失的需求，是在换个名字定需求。
