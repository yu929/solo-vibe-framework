# 1 · 需求收敛

> 把一句话想法整理成收敛到字段级的完整 PRD。顺序是：讨论 → 写 PRD → 抛原型验字段 → 反写。
>
> 原型里验证出的内容最后要反写进 PRD，否则后续仍会使用验证前的需求。

## 步骤

### 步骤 1 · 需求讨论

```
/grill-with-docs

我想做 <一段话，不用组织>。
先把你能自己查的查了，剩下真需要我拍板的一次列出来，每题给个推荐答案。
```

> 未实跑。

它会按 frontier 组织问题：前置条件已定的放在这一轮，仍依赖其他决定的留到下一轮。环境事实应由它自己查，不用交给你判断。

#### 收尾：把问出来的东西分四类

讨论结束后，要明确做一次分流。grilling 会一直问到 frontier 为空，内容通常比一份文档能容纳的多；这不是文档太小，而是这些内容本来就有不同去处：

| 问出来的 | 落哪 | 为什么 |
|---|---|---|
| 环境事实：现有仓库有什么、某个库支不支持、这个格式能否解析 | 不记录 | 查完用于当前判断即可，长期保存很快会过期 |
| 术语：这个东西在本项目里叫什么 | `CONTEXT.md` | 由 `domain-modeling` 维护 |
| 需求边界：做什么、不做什么、给谁用、何时算完成 | 完整 PRD | PRD 负责说明要做什么 |
| 有取舍的决定：另一个选项也能走通，但被否掉了 | `docs/adr/` | ADR 负责说明为什么这样选 |

分不清时就问：它是事实、术语、范围，还是选择？只有最后一类进 ADR。

ADR 的准入卡三条判据，权威源在 `~/.claude/skills/domain-modeling/SKILL.md`，**三条全中才写**。本仓不再转抄，因为转抄出来的第二份会先过期。

```
刚才问出来的，按四类分：环境事实（丢掉）/ 术语（进 CONTEXT.md）/
需求边界（进 PRD 哪一节）/ 有取舍的决定（进 docs/adr/）。
第四类按 domain-modeling 的三条判据筛，缺一条就不写，并告诉我它缺哪条。
```

> 未实跑。最后一句是防它把什么都判成「有取舍」。让它说出缺哪条判据，比让它自己把关有效。

### 步骤 2 · 写完整 PRD

用 `create-prd-skill`，产物落 `docs/discovery/prd.md`。

它会按 L1–L4 调整文档深度，先确认分级是否合理。小需求误判成 L4，会多出十几章没人读的内容；大需求误判成 L1，则会漏掉需要拍板的问题。

确认方法：读完后，你能说出这一阶段让用户完整做成什么，以及这一阶段明确不做什么。

再检查一次：有没有本可选择另一种做法、但最后被否掉的决定只留在对话里？有的话，前面的分流漏了一条。

### ★ 拍板 1：范围 + 明确不做

这里值得慢一点。范围定错，后面的原型、设计和实现都会跟着偏。

拍之前问自己两个问题：

1. 「不做」里的东西，真的可以先不要吗？
2. 范围是不是一条**能跑通的链路**？说不出「用户从哪进来、做完什么、看到什么结果」，那它还是一批功能。

> 这里没有 approved 字段。你读完并确认后，直接进入下一步。

### 步骤 3 · 抛原型验字段

只在纸上推不动时做原型，例如需要验证状态机在特定输入下的变化、字段是否够用，或异常态该如何表达。

```
先别建 task。我要验证 <一件具体的事>。
用 prototype 的 LOGIC 分支写个最小的东西验证它，不要进 src/，验完就删。
```

> 未实跑。

做原型时守住三条边界：

1. **不建 task**，它不是一次交付，是一次问答
2. **不进 `src/`**，验完就删
3. **走 LOGIC 分支**。`prototype` 第一步是 "Pick a branch"，没有任何机制挡得住它选 UI 分支，而 UI 分支会在真项目路由里开几个变体，跟下一篇的全量高保真是两条路。发现它跑偏就当场拉回来

如果说不出要验证什么、什么结果算通过，就先别做原型。那会变成没有边界的提前实现。

### 步骤 4 · 反写 PRD

把原型暴露出的字段、状态和边界情况合进 PRD 正文。

按 delta 修改正文，不要在末尾追加补充说明。使用 ADDED / MODIFIED / REMOVED 标记，格式和理由见 `.trellis/spec/guides/source-of-truth.md`（编辑 `docs/discovery/**` 时会自动注入）。

在阶段边界集中反写一次。每验证一点就追加一次，PRD 很快会变成对话记录，读者还得自己拼出现状。

确认方法：PRD 中每个会出现在 UI 上的字段，都写清楚取值范围和空值表现。没有写清楚的部分，下一步画高保真时只能靠猜。

## 我该在哪停下来看

| # | 看什么 | 漏了会怎样 |
|---|---|---|
| 1 | 范围 + 明确不做（★ 拍板 1） | 范围错了，后面的原型、设计和实现都会跟着偏 |
| 2 | 有取舍的决定进了 `docs/adr/` 没有 | 对话下个 session 就没了，半年后自己推翻自己 |
| 3 | **字段级收敛到了没有** | 下一篇的高保真会替你猜，而且猜完就被当成已定 |

第 3 条最容易被忽略，因为当下看不出问题。往往做完十几片后，才会以「结构不对」的形式暴露出来。

## 常见卡点

### 「brainstorm 一直问我问题」

设计如此。见[场景首页](README.md)「五件反复出现的事」第四条。

### 「grill 问了十几轮，PRD 装不下」

装不下是对的。十几轮问出来的东西分四类，只有一类该进 PRD，见步骤 1 的收尾。

判断 PRD 是不是被撑坏了，看两个信号：

- 出现了「为什么这么定」的段落 → 那是 ADR 的内容
- 出现了具体的屏和交互序列 → 那是高保真的内容

两个都没有、还是太长 → **这才是范围太大**，回去砍「明确不做」。

### 「PRD 写完之后又想改」

直接改即可，这里没有需要作废的审批状态。

PRD 要长期保留，并随阶段目标更新。Trellis 的其他产物都不保存完整的产品全貌，删掉 PRD 就会丢掉这一层信息。

### 「Trellis 一直问要不要建 task」

这几轮里嫌吵就用 `no-trellis`，见 [`../setup/04-workflow-prompts.md`](../setup/04-workflow-prompts.md) 的常见卡点。
