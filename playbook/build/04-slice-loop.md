# 4 · 逐片进 Trellis

> 一片一个循环，做完回到 `slices.md` 取下一片。这一篇只讲 **Trellis 没有、而你必须做**的那几处。

## 一片的完整循环

```
建 task
  │
Phase 1 Plan ──── brainstorm 一问一答 → prd.md / design.md / implement.md
  │               本片定稿屏 + 本片碰到的每一层 spec → implement.jsonl
  │                                   ★ 你批准 planning summary，它才 start
  │
  ══════════ 从这里往后它一路自己跑 ══════════
  │
Phase 2 Execute ─ 派 implement 子 agent → 派 check 子 agent
  │                                   ★ 人工验收 ← 流程里没有，你得手动插
  │
Phase 3 Finish ── update-spec → 提交计划（唯一的自动停顿）→ 归档 + journal
                                      ★ 看它改了哪几条 spec
```

Phase 2 到 Phase 3 是连着跑完的，中间每一步都被 Trellis 标成 `[required]`，AI 自己往下走。唯一会主动停下来问你的是 Phase 3 的提交计划。它列出准备分几批提交、哪些文件是它改的、哪些它不认识，等你回一个「ok」。

所以人工验收不会自己发生。**你不插，它就不存在。**

中断后接着干：`/trellis:continue`。

## 步骤

### 步骤 1 · 建 task

```
按 slices.md 的第 <N> 片建 task。
```

> 未实跑。

### 步骤 2 · 盯住 `implement.jsonl`

这是这一篇最要紧的一件事，而且漏了没有任何症状。

实现是子 agent 干的，它在一个全新的 context window 里，只拿得到 `implement.jsonl` 列出来的文件内容。`prd.md` 里写一行定稿路径不算。那只是一个字符串，混在好几份规范中间很容易被略过。

两类东西必须进去：

1. **本片对应的高保真屏**，路径取自 `slices.md` 切片清单第四列。**只列这一片的**，全量定稿会撑爆子 agent 的 context
2. **本片碰到的每一层**，它的 `.trellis/spec/<层>/index.md`，以及那份 index 指向的同层文件

**查法**：打开 task 目录的 `implement.jsonl`，看有没有 `design-system/screens/` 下那几条。没有就是它。

**补法**：

```
把这一片的定稿屏加进 implement.jsonl，然后重做实现。
```

> 未实跑。第一条已实跑得出，第二条未实跑验证。

漏了长什么样：定稿画了、`prd.md` 也引用了，实现出来照样不是定稿的结构，**看起来像执行不认真**。

### ★ 拍板 4：planning summary

Trellis 自带的硬门禁，没有你的显式批准不许 `task.py start`。这是整条链上唯一真正拦得住事的地方。

看两样：这一片的边界对不对，`implement.jsonl` 里那两类文件在不在。

### ★ 拍板 5：本片验收

**Trellis 没有这一步。** 它的 check 验的是「代码符合规范和 `prd.md` 的文字」，AI 对着文档查 AI 写的代码。整条链上没有任何一步是**人**确认「这东西真的做成了我要的事」。

**插在哪**：check 绿了之后、`update-spec` 之前。三个理由：

- check 已经把不合规范的清掉了，剩下的才值得你亲自看
- 你亲手跑一遍踩到的坑，正是 `update-spec` 最好的素材，顺序天然对得上
- 还没提交，改起来最便宜

**清单不用另写**：`prd.md` 的验收标准那一节就是。brainstorm 的收敛门强制要求它「描述可观测的结果」，那节东西写下来就是给人验的。

**重点验负向用例。** 正向路径 AI 大概率做对了；「不该看见的人看不看得见」「不该能做的操作拦没拦住」才是最容易漏、也最贵的一类。人的本能是只走主链路。

**不过的话，先分清是哪一类**：

| 现象 | 退到哪 | 贵不贵 |
|---|---|---|
| 没照 `prd.md` 做 | 退回实现，重做 | 便宜 |
| 照 `prd.md` 做了，但那不是你要的 | 退回 Phase 1 改 `prd.md`，再重做 | 贵得多 |

第二类**反复出现就是走查失效的信号**。高保真走查存在的全部意义就是把这类返工提前到开工前。真遇上了别只修这一片，回头看 [`02-hifi.md`](02-hifi.md) 那一步为什么没拦住。

### ★ 拍板 6：Finish 改了哪几条 spec

`trellis-update-spec` 会把这一片的经验升级进 `.trellis/spec/`。**它跑的时候要多看一眼**，AI 倾向于把一次性决定写成永久约定。

判据是：**下次遇到同类情况，还该这么做吗？** 只此一次的，不进。

答「不该」也未必是丢掉。三个去处别混：

| 这次的新东西 | 落哪 |
|---|---|
| 下次同类情况还该这么做的编码约定 | `.trellis/spec/`，走 `update-spec` |
| 有取舍的架构决定 | `docs/adr/`，卡三条判据 |
| 只此一次 | 哪也不进 |

## 编码期发现的东西

AI 在实现或调试时会发现「这个约定其实不对」「这里有坑 spec 没写」。规则是**先记 finding，确认之后才升级**，四字段格式和「值不值得记」的判据都在 `.trellis/spec/guides/review-adjudication.md`。

**你要判的是三件事**：

| 判什么 | 判据 |
|---|---|
| 值不值得记 | 别的 session 会不会**因为 spec 没写**而重犯同一个错？大部分 bug 不需要记，bug 说明代码没做到已有约定，约定本身没变 |
| 升到哪一层 | 换一个同轨的**别的项目**还成立吗？成立 → 框架仓的源真；不成立但本项目后面还要用 → 本项目 `.trellis/spec/`；一次性 → 留在 `findings/` |
| 什么时候升 | 后两类当场升。**第一类攒到阶段末批量做**，见 [`05-checkpoint.md`](05-checkpoint.md) |

**task 内绝不碰框架仓。** `trellis-update-spec` 不知道 spec 是从 registry 装来的，它只写项目里那份拷贝。把经验带回框架仓再装回来是**跨仓操作**，只有人能做。

## 常见卡点

### 「第三片的列表页跟第一片长得不一样」

回去看 `design-system/screens/`。全量定稿存在的意义就是消除这个问题。不一致说明实现期没读到定稿，回步骤 2 查 `implement.jsonl`。

### 「实现出来的前端不堪入目」

先分是哪一种：

| 现象 | 归谁 |
|---|---|
| 默认样式，但布局和信息层级是对的 | `design-system/MASTER.md` 没被读到，查 `implement.jsonl` |
| 布局或层级本身就烂 | 这一片的结构债，退回改 `prd.md` |

**两种同时出现很正常。** 顺序不能反：先定结构，再上视觉。

### 「小改动要不要建 task」

一句话能答完、不改文件、不需要调研的，不建。Trellis 自己的规矩就是这样。

**但改动跨多个文件、或需要先调研的，建**，你需要那份跨 session 记忆。
