# 5 · 项目级检查点

> 停下来看看产品全貌。它由条件触发，不按双周之类的固定节奏举行。

## 什么时候用

满足任一条：

- 连续做完了 3–5 个切片
- 阶段目标达成了
- 准备发一个版本
- 产品目标本身变了
- 架构开始阻碍开发：连着两片都在绕同一个东西
- 文档和代码明显对不上了

## 为什么需要这一篇

Trellis 管单个 task，不负责跨 task 盘点产品，所以逐片推进还需要这一层。

`finish-work` 的四步是查状态、检查 git、执行 `task.py archive`、写 journal，只处理当前 task；`trellis-update-spec` 也一样。两者都不会问产品层的问题。

跑完许多 task 后，你会有编码规范、归档记录和时间流水，但这些材料仍不会直接说明产品现在的整体状态。

检查点补的就是这张产品全景图。

## 开始之前

- [ ] 手上没有进行中的 task。有就先 Finish，别在半截上盘点
- [ ] `docs/discovery/slices.md` 还在

## 步骤

### 步骤 1 · 让 AI 先摊开现状

```
做一次项目检查点。先只做汇总，不要给建议：
1. 列出 .trellis/tasks/archive/ 里已完成的切片，每个一句话
2. 对照 docs/discovery/slices.md 的切片清单，标出：做了但不在清单里的、清单里还没做的
3. 列出 .trellis/spec/ 里最近新增的约定
4. 列出 finding 记录里状态是 open 的条目（落点跟随本项目的约定，通常是 findings/ 或已知问题文件）
5. 列出 docs/adr/ 里写了「什么时候回来重看」的条目，逐条说触发条件到了没有
6. 不要下结论
```

> 未实跑。

先不让 AI 给建议，是为了把事实汇总与判断分开。两件事一起做时，汇总内容很容易被它自己的结论带偏。

确认方法：看着汇总表，你能想起每个切片当时做了什么。

### 步骤 2 · 七个问题

七个问题逐个回答。AI 可以帮忙找证据，但结论由你来定。

| # | 问题 | 答「不」的时候做什么 |
|---|---|---|
| 1 | 当前阶段目标还成立吗 | 改 `slices.md` 第 1 节，说明为什么变 |
| 2 | 已完成的切片加起来，构成一件用户能完整做成的事了吗 | 找出断在哪一环，那就是下一片 |
| 3 | 有没有无意识扩张：做了但不在切片清单里的 | 每条问一遍「当初该做吗」。该，补进 PRD；不该，记下来别再犯 |
| 4 | 架构和交互还一致吗 | 不一致的记 finding，不要顺手改。先分清是哪一层，见下 |
| 5 | 测试覆盖到当前核心路径了吗 | 补测试，那是下一片的一部分 |
| 6 | 有没有该删掉而不是继续实现的需求 | 移进 PRD 的「明确不做」，写原因 |
| 7 | 能不能发一个稳定版本了 | 说得出还差什么，那就是下一片 |

第 3 问用来抓逐片推进中悄悄长出的范围，第 6 问则直接减少工作量。这两问都值得慢下来回答。

第 4 问答「不」时，先分清不一致出在哪一层：

- 某一片实现跑偏了 → 记 finding，当下一片的候选。这是常态
- 承重决策本身不成立了：数据归属、权限边界、模块切分、长期契约 → 记一条 finding 解决不了，打一次 `/design-review`，见 [`06-off-path.md`](06-off-path.md)

判据：**修它要不要动已经做完的好几片？** 要，就是承重层。

承重决策通常记录在 `docs/adr/`。先读当初为什么这样选，再判断是否要推翻。很多所谓「架构不对」，其实是原来的前提变了，例如用户从一人变成多人，或者出现了第二个数据源。遇到这种情况，新写一条 ADR 说明替代了哪条，不要改掉旧记录。

如果连续两个切片都在绕同一个障碍，问题通常出在承重决策，而不是两个切片分别没有做好。

### 步骤 3 · 阶段末，把该回写的 finding 批量带回框架仓

只在阶段目标达成时做这一步；普通的 3–5 片检查点跳过。

`findings/` 里有一类经验是**换一个同轨的别的项目也成立**的。它们的源真不是项目里那份 `.trellis/spec/` 拷贝，是框架仓 `specs/<track>/`。

一条只出现过一次的经验，很难判断是通用规律还是当前情境的特例。留到阶段末放在一起看，更容易分清重复出现的模式和偶然现象，也避免发现问题后立刻把它写成规则。

这是跨仓操作，需要你亲自处理：

1. 在项目仓的 finding 记录里挑出「换个项目还成立」的那些
2. 到框架仓改 `specs/<track>/` 的对应文件，合进 `main`
3. 回项目仓 `trellis update`
4. 把回写过的 finding 状态改成已升级，留一条指向 spec 规则的链接

**第 3 步要看一眼输出**：`.trellis/spec/` 里被你本地改过的文件，update 会逐个问你要不要覆盖，不会静默替换。

**第 2 步不能省略合进 `main`**：`--registry` 拉的是写死的 `main`，改在分支上装不回来。见 [`../../references/install-mechanics.md`](../../references/install-mechanics.md)。

### 步骤 4 · 回写 `slices.md`

检查点完成后，只更新 `docs/discovery/slices.md`：

- 第 1 节阶段目标：达成了就写下一阶段的，变了就改
- 第 2 节切片清单：做完的划掉，新识别的加上并排阻塞边
- 第 3 节 frontier：重算一次，别从上往下数

范围变化落 PRD，不落这里。

不要新建检查点报告、review 记录或状态字段。检查点是一次盘点，结论应直接写回持续使用的 `slices.md`；另存一份很快就会无人读取。

## 我该在哪停下来看

| # | 拍什么 | 为什么 |
|---|---|---|
| 1 | 阶段目标还成立吗 | 答「是」就一分钟结束；答「否」，检查点才需要继续展开 |
| 2 | 哪些该砍 | 这会直接减少工作量，也最容易被跳过 |
| 3 | 哪些 finding 该带回框架仓 | 不带回去，下一个项目会从头再踩一遍 |
| 4 | 下一阶段目标是什么 | 不定下来，下一批切片又会变成孤立功能 |

## 常见卡点

### 「每次都答『还成立』，感觉在走过场」

那就把频率调低，5 片一次而不是 3 片，但**别取消**。

第 1 问经常会答「是」，这很正常。更容易发现问题的通常是第 3、4、6 问：范围扩张、结构不一致和应当删掉的需求。第 1 问只是一道成本很低的复核。

### 「AI 直接给了一堆改进建议」

打断，让它先只做汇总。见步骤 1。

先拿到不带判断的现状表，再自己下结论。这样你能看见完整证据，也更容易发现 AI 是否漏了与建议相冲突的内容。

### 「发现前面某一片做错了」

**不要顺手改。** 记 finding，当成下一片的候选。

检查点只做盘点，不在这里改代码。边盘点边施工，很容易把它变成一次没有边界的重构。

### 「`slices.md` 和实际做出来的东西差太远」

那就按**现在实际有什么**重写第 1、2 节。

它的价值是「现在整体是什么」，不是「当初计划是什么」。当初的计划在 git 里。
