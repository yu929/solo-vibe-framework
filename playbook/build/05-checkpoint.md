# 5 · 项目级检查点

> 停下来看一眼全貌。非时间盒。不是每两周一次，是达到某个条件时一次。

## 什么时候用

满足任一条：

- 连续做完了 **3–5 个切片**
- **阶段目标达成了**
- 准备发一个版本
- 产品目标本身变了
- **架构开始阻碍开发**：连着两片都在绕同一个东西
- 文档和代码明显对不上了

## 为什么需要这一篇

Trellis 没有这一层，而逐片推进特别需要它。

它的 `finish-work` 看起来像收尾，其实只有四步：查状态 → 检查 git 干不干净 → `task.py archive` → 写 journal。零个产品问题，而且只管当前这一个 task。`trellis-update-spec` 也是 task 级的。

所以跑五十个 task 之后，你手上有一堆编码规范、一堆已归档的单次改动、一条时间流水，没有任何一处回答「这个产品现在整体是什么」。

逐片推进的代价就是没人看全貌，检查点是唯一的补救。

## 开始之前

- [ ] 手上没有进行中的 task。有就先 Finish，别在半截上盘点
- [ ] `docs/discovery/slices.md` 还在

## 步骤

### 步骤 1 · 让 AI 先摊开现状

```
做一次项目检查点。先只做汇总，不要给建议：
1. 列出 .trellis/tasks/archive/ 里已完成的切片，每个一句话
2. 对照 docs/discovery/slices.md 的切片清单，标出：做了但不在清单里的、清单里还没做的
3. 列出 .trellis/spec/ 里最近新增的约定
4. 列出 finding 记录里状态是 open 的条目（落点跟随本项目的约定，通常是 findings/ 或已知问题文件）
5. 列出 docs/adr/ 里写了「什么时候回来重看」的条目，逐条说触发条件到了没有
6. 不要下结论
```

> 未实跑。

**为什么要求「不要给建议」**：让它同时汇总和判断，它会把汇总裁剪成支持自己判断的样子。分两步，第一步的产物你才敢信。

**怎么确认这步成了**：你看着那张表，能想起每一片当时在干什么。

### 步骤 2 · 七个问题

一个一个过。**这是给你自己回答的**。AI 可以帮你找证据，答案得你来定。

| # | 问题 | 答「不」的时候做什么 |
|---|---|---|
| 1 | **当前阶段目标还成立吗** | 改 `slices.md` 第 1 节，说明为什么变 |
| 2 | 已完成的切片加起来，构成一件用户能完整做成的事了吗 | 找出断在哪一环，那就是下一片 |
| 3 | **有没有无意识扩张**：做了但不在切片清单里的 | 每条问一遍「当初该做吗」。该，补进 PRD；不该，记下来别再犯 |
| 4 | **架构和交互还一致吗** | 不一致的记 finding，不要顺手改。**先分清是哪一层**，见下 |
| 5 | **测试覆盖到当前核心路径了吗** | 补测试，那是下一片的一部分 |
| 6 | **有没有该删掉而不是继续实现的需求** | 移进 PRD 的「明确不做」，写原因 |
| 7 | **能不能发一个稳定版本了** | 说得出还差什么，那就是下一片 |

**第 3 问和第 6 问最值钱。** 前者抓的是逐片模式最容易积累的病，后者是唯一一个会让工作量**变少**的问题，而它几乎总是被跳过。

第 4 问答「不」时，先分清不一致出在哪一层：

- **某一片实现跑偏了** → 记 finding，当下一片的候选。这是常态
- **承重决策本身不成立了**：数据归属、权限边界、模块切分、长期契约 → 记一条 finding 解决不了，打一次 `/design-review`，见 [`06-off-path.md`](06-off-path.md)

判据：**修它要不要动已经做完的好几片？** 要，就是承重层。

承重决策通常在 `docs/adr/` 里有条目，**先去读当初的「为什么」再判断**。很多「架构不对」其实是当初的取舍换了前提：那时只有一个人用、那时没有第二个数据源。前提变了就推翻，在 `docs/adr/` 里**新写一条**说明推翻了哪条，别改旧条目。

这也正好对上本篇的触发判据「连着两片都在绕同一个东西」，那通常是承重决策的问题，不是那两片各自没做好。

### 步骤 3 · 阶段末，把该回写的 finding 批量带回框架仓

**只在「阶段目标达成」那一次检查点做，每 3–5 片那次不做。**

`findings/` 里有一类经验是**换一个同轨的别的项目也成立**的。它们的源真不是项目里那份 `.trellis/spec/` 拷贝，是框架仓 `specs/<track>/`。

**为什么攒到阶段末**：一条只经历过一次的经验，你没有办法判断它是通用的，还是那一次特有的。逐条回写就是发现方兼任裁决方，这正是 finding 机制要防的事。攒一批放在一起看，才分得出哪些是同一个模式，哪些只是碰巧一起出现。

这是**跨仓操作**，只有你能做：

1. 在项目仓的 finding 记录里挑出「换个项目还成立」的那些
2. 到框架仓改 `specs/<track>/` 的对应文件，合进 `main`
3. 回项目仓 `trellis update`
4. 把回写过的 finding 状态改成已升级，留一条指向 spec 规则的链接

**第 3 步要看一眼输出**：`.trellis/spec/` 里被你本地改过的文件，update 会逐个问你要不要覆盖，不会静默替换。

**第 2 步不能省略合进 `main`**：`--registry` 拉的是写死的 `main`，改在分支上装不回来。见 [`../../references/install-mechanics.md`](../../references/install-mechanics.md)。

### 步骤 4 · 回写 `slices.md`

检查点唯一的产物是更新后的 `docs/discovery/slices.md`：

- 第 1 节阶段目标：达成了就写下一阶段的，变了就改
- 第 2 节切片清单：做完的划掉，新识别的加上并排阻塞边
- 第 3 节 frontier：重算一次，别从上往下数

范围变化落 PRD，不落这里。

**不新建文件。** 不建检查点报告、不建 review 记录、不建状态字段。检查点是一个动作，不是一份产物。它的结论必须落进那份一直被读的文件，落进别处就等于没落。

## 我该在哪停下来看

| # | 拍什么 | 为什么 |
|---|---|---|
| 1 | **阶段目标还成立吗** | 这是整个检查点的意义。答「是」就一分钟结束，答「否」才是它值回票价的时候 |
| 2 | **哪些该砍** | 唯一让工作量变少的问题，也是最容易跳过的 |
| 3 | **哪些 finding 该带回框架仓** | 不带回去，下一个项目从头再踩一遍 |
| 4 | **下一阶段目标是什么** | 不定下来，下一批切片又会变成一批孤立功能 |

## 常见卡点

### 「每次都答『还成立』，感觉在走过场」

那就把频率调低，5 片一次而不是 3 片，但**别取消**。

第 1 问答「是」是常态，不是走过场。七问里真正会抓到东西的通常是第 3、4、6：扩张、不一致、该砍的。第 1 问是个便宜的保险。

### 「AI 直接给了一堆改进建议」

打断，让它先只做汇总。见步骤 1。

一份没有判断的现状表，你自己看两分钟就有结论，而且那个结论是你的。AI 给的建议清单读起来更专业，但你没法验证它是不是把汇总裁剪成了支持结论的样子。

### 「发现前面某一片做错了」

**不要顺手改。** 记 finding，当成下一片的候选。

检查点是**盘点**，不是施工。在检查点里开始改代码，它就会变成一次没有边界的重构，那正是这套流程要防的事。

### 「`slices.md` 和实际做出来的东西差太远」

那就按**现在实际有什么**重写第 1、2 节。

它的价值是「现在整体是什么」，不是「当初计划是什么」。当初的计划在 git 里。
