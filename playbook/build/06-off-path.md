# 6 · 不在主线上的四个入口

> 主线是「需求 → 定稿 → 切片 → 逐片」。遇到下面四类工作时，从各自的入口开始。

## 走哪一个

| 你现在要做的 | 走哪 |
|---|---|
| 结构已定，加一个新能力 | [加一片](#加一片) |
| 行为不符合预期，能力集不变 | [修 bug](#修-bug) |
| 改一个到处都在用的符号、字段或类型 | [宽重构](#宽重构) |
| 反复审同一份设计，停不下来 | [`design-review` 逃生舱](#design-review-逃生舱) |

如果说不出这次改动属于哪个阶段目标，先回 [`05-checkpoint.md`](05-checkpoint.md) 盘点一次全貌。

## 加一片

适用条件：结构已经定下，这次增加的是一项新能力，而且完成后用户能独立做成一件事。

不是一片的两种：

- **它是好几片** → 先拆开，排进 `slices.md` 的阻塞边，一片一片来
- **它太小了**：一句话能答完、不改文件 → 直接说，不建 task

### 步骤

1. **只做增量，别重排整张表。** 打 `/vertical-slicing`，告诉它 `slices.md` 已存在、这次只加一片。它会跳到定稿那一步，其余行不动
2. **第四列照填。** 定稿里没有对应的屏，先回 [`02-hifi.md`](02-hifi.md) 补，别让它空着
3. 之后走 [`04-slice-loop.md`](04-slice-loop.md)，和第一片一模一样

### 它和主线的差别

差别只在于是否需要先收敛需求。已有 PRD 和定稿就从这里开始，否则回 [`01-discovery.md`](01-discovery.md)。

如果新能力需要新屏，补进定稿即可。这不算重新走查，也没有审批状态需要作废。

## 修 bug

适用条件：某个行为不符合预期，修复前后产品能力不变。

- 「这个功能缺了一块」→ 那是加一片
- 「整个方向不对」→ 先走 [`05-checkpoint.md`](05-checkpoint.md)

### 开始之前

- [ ] **能稳定复现。** 复现不了就先别修，你无法验证修好了
- [ ] 知道正确行为该是什么。说不出来的话，这是需求问题不是 bug

### 步骤

1. 先定位，再修改。AI 很容易跳过定位直接试修，症状暂时消失，根因却仍然存在

   ```
   先说清楚根因是什么，我确认后再改。
   ```

   > 已实跑（这一句不依赖 Trellis 的任何细节）。

   判断方法：看它的解释能否预测这个 bug 还会在哪些条件下出现。能预测，说明找到了根因；说不出来，通常还在试错

2. 确认根因之后再改，改动范围要和根因对得上
3. **你自己复现一遍。** AI 说「已修复」不算数
4. 判断要不要记 finding

### 要不要记 finding

默认不记。普通 bug 说明代码没有做到已有约定，并不代表约定本身需要修改。

例外是 bug 暴露了 spec 的缺口，也就是此前没人规定这种情况该怎么办。判断时问：下一个 session 会不会因为 spec 没写而重犯？

会，就记 finding，**不是直接改 spec**。四字段格式和升级规则在 `.trellis/spec/guides/review-adjudication.md`，你要判的三件事在 [`04-slice-loop.md`](04-slice-loop.md)。

### 要不要建 task

一句话能答完、不改文件、不需要调研的，不建。

**改动跨多个文件、或需要先调研的，建**，你需要那份跨 session 记忆。

## 宽重构

适用条件：一次机械改动会影响全仓，例如修改共享符号的类型，或重命名一个被广泛使用的字段。

**不要把它当成一片纵向切片来切。** 硬拆之后每一片都会碰到它，却没有一片能独立完成迁移，中间态根本编译不过。

走 expand–contract：先加新的、让两者并存，再把调用点一处处搬过去，最后删旧的。完整做法在 `~/.claude/skills/vertical-slicing/references/wide-refactor.md`。

expand–contract 的每张工单仍写进 `slices.md` 的切片清单。切片清单是全仓唯一记录阻塞边的地方，而这组工单正靠阻塞边维持顺序。这类工单有两个例外：第三列写技术上可观测的结果，不写用户能做成什么；第四列留空，因为宽重构通常不对应具体屏。

## `design-review` 逃生舱

它不在主流程里，也不会自动触发。大多数切片不需要单独做设计准入，Trellis 的 planning summary 已经够用。

它处理的是评审无法收敛：换了几个 session 仍在反复审同一份设计，修掉一些问题后每轮又冒出新的，也说不清何时结束。

它会冻结输入，用问题台账、证据门槛、P0–P3 分级和停止规则把评审收在两轮内。之后从切片实现和测试中继续收集反馈，成本更低，证据也更直接。

完整触发条件以 skill 的 When to use it 一节为准，这里不再复制一份容易过期的短清单。

**怎么喊**：打 `/design-review`。它带 `disable-model-invocation`，AI 够不着，也不会因为你随口说了「审一下」就上场。只有你打这个名字才启动。

**它不做三件事**：

- 不做需求评审。那是 [`01-discovery.md`](01-discovery.md) 和高保真走查的事
- 不做代码评审。那是 Trellis 的 check 和代码评审的事
- 不接编码期发现的「这条约定不对」。那是四字段 finding
