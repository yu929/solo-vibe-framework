# 6 · 不在主线上的四个入口

> 主线是「需求 → 定稿 → 切片 → 逐片」。这四件事各自从别的地方进来。

## 走哪一个

| 你现在要做的 | 走哪 |
|---|---|
| 结构已定，加一个新能力 | [加一片](#加一片) |
| 行为不符合预期，能力集不变 | [修 bug](#修-bug) |
| 改一个到处都在用的符号、字段或类型 | [宽重构](#宽重构) |
| 反复审同一份设计，停不下来 | [`design-review` 逃生舱](#design-review-逃生舱) |

说不出这次改动属于哪个阶段目标 → 先回 [`05-checkpoint.md`](05-checkpoint.md) 盘一次全貌。

## 加一片

**判据**：结构已定，这次加的是新能力，而且它是**一片**：做完之后有一件事是用户能真正做成的。

不是一片的两种：

- **它是好几片** → 先拆开，排进 `slices.md` 的阻塞边，一片一片来
- **它太小了**：一句话能答完、不改文件 → 直接说，不建 task

### 步骤

1. **只做增量，别重排整张表。** 打 `/vertical-slicing`，告诉它 `slices.md` 已存在、这次只加一片。它会跳到定稿那一步，其余行不动
2. **第四列照填。** 定稿里没有对应的屏，先回 [`02-hifi.md`](02-hifi.md) 补，别让它空着
3. 之后走 [`04-slice-loop.md`](04-slice-loop.md)，和第一片一模一样

### 它和主线的真实差别

**只有一处：要不要先收敛需求。** 已经有 PRD 和定稿了就走这里，还没有就回 [`01-discovery.md`](01-discovery.md)。

新能力带出了新屏，那就是定稿要补的部分，不是「重新走查」，没有审批要作废。

## 修 bug

**判据**：某个行为和预期不一致，修完之后**能力集不变**。

- 「这个功能缺了一块」→ 那是加一片
- 「整个方向不对」→ 先走 [`05-checkpoint.md`](05-checkpoint.md)

### 开始之前

- [ ] **能稳定复现。** 复现不了就先别修，你无法验证修好了
- [ ] 知道正确行为该是什么。说不出来的话，这是需求问题不是 bug

### 步骤

1. **先定位，再改。** 这是这个入口唯一容易出事的地方：AI 很容易跳过定位直接改，改完症状消失但根因还在

   ```
   先说清楚根因是什么，我确认后再改。
   ```

   > 已实跑（这一句不依赖 Trellis 的任何细节）。

   **判据**：它的解释能不能预测这个 bug 在别的什么条件下也会出现？能，说明定位到了；说不出来，那是在试

2. 确认根因之后再改，改动范围要和根因对得上
3. **你自己复现一遍。** AI 说「已修复」不算数
4. 判断要不要记 finding

### 要不要记 finding

**默认不要。** 一个 bug 说明代码没做到已有约定，约定本身没变。

**例外**：这个 bug 暴露了 spec 的缺口：「原来没人规定过这种情况该怎么办」。判据是：下次别的 session 会不会因为 spec 没写而重犯？

会，就记 finding，**不是直接改 spec**。四字段格式和升级规则在 `.trellis/spec/guides/review-adjudication.md`，你要判的三件事在 [`04-slice-loop.md`](04-slice-loop.md)。

### 要不要建 task

一句话能答完、不改文件、不需要调研的，不建。

**改动跨多个文件、或需要先调研的，建**，你需要那份跨 session 记忆。

## 宽重构

**判据**：一次机械改动，影响面铺满全仓。改一个共享符号的类型、重命名一个到处都在用的字段。

它不进 `slices.md` 的切片清单。 硬塞进纵向切片会让每一片都是红的：每一片都碰它，每一片都改不完。

走 expand–contract：先加新的、让两者并存，再把调用点一处处搬过去，最后删旧的。完整做法在 `~/.claude/skills/vertical-slicing/references/wide-refactor.md`。

**第四列通常为空**，这是宽重构唯一合法的空第四列，它本来就不对应任何屏。

## `design-review` 逃生舱

它不在主流程里，主线没有一处会自动用到它。 这是设计如此，不是漏了：逐片推进下大部分切片不需要独立的设计准入，Trellis 的 planning summary 门禁就够了。

它治的不是「审得不够细」，是「停不下来」。 症状很好认：换了几个 session 反复审同一份设计，问题越修越多，每轮都冒出新的，你说不出什么时候算审完。

它用冻结输入、问题台账、证据门槛、P0–P3 和明确的停止规则强制收敛，最多两轮，然后把反馈渠道转向切片实现和测试，那里的反馈更便宜也更真。

完整的触发条件在 skill 自己的 When to use it 一节，那里是权威源。 这里不列第二份短清单，短清单迟早漏掉一种。

**怎么喊**：打 `/design-review`。它带 `disable-model-invocation`，AI 够不着，也不会因为你随口说了「审一下」就上场。只有你打这个名字才启动。

**它不做三件事**：

- 不做需求评审。那是 [`01-discovery.md`](01-discovery.md) 和高保真走查的事
- 不做代码评审。那是 Trellis 的 check 和代码评审的事
- 不接编码期发现的「这条约定不对」。那是四字段 finding
