# 场景三 · Fix Bug

> 行为不符合预期，不新增能力。
>
> **本文件第一版只有骨架**，细节等实跑后补。

## 什么时候用这个场景

**判据**：某个行为和预期不一致，修完之后**能力集不变**。

不走这里的情况：

- 「这个功能缺了一块」→ 那是 feat，走 [`02-feat-dev.md`](02-feat-dev.md)
- 「整个方向不对」→ 走 [`04-checkpoint.md`](04-checkpoint.md) 先盘一次全貌，再决定

## 和 Feat Dev 的真实分岔

**要不要回写 spec。** fix **通常不要**——一个 bug 说明代码没做到已有约定，约定本身没变。

**例外**：这个 bug 暴露了 spec 的缺口（"原来没人规定过这种情况该怎么办"）。那不是直接改 spec，是走 **finding 流程**：

```markdown
## F-<日期>-<序号>：<一句话>

- **现象**：观察到什么（不是结论）
- **证据**：怎么复现 / 在哪看到的
- **该改哪个 spec**：具体文件；不确定就写「待定」
- **状态**：open / 已升级进 spec / 已拒绝（附理由）
```

**为什么不让 AI 直接改 spec**：那等于让召回方兼任裁决方。一次调试里的临时结论会变成永久约定，spec 会在几周内被填满未经检验的经验。规则见 [`review-adjudication.md`](../specs/universal/guides/review-adjudication.md)。

注意 Trellis 的 Phase 3 有个 `trellis-update-spec` 会主动把本次经验升级进 `.trellis/spec/`——**那一步是升级动作，前提是这条经验你已经确认过**。它跑的时候要多看一眼。

## 开始之前

- [ ] **能稳定复现**（复现不了就先别修——你无法验证修好了）
- [ ] 知道正确行为该是什么（说不出来的话，这其实是需求问题不是 bug）

## 步骤（骨架）

| # | 我敲什么 | AI 产出 | 怎么确认成了 |
|---|---|---|---|
| 1 | 描述现象 + 复现步骤 | Trellis 问要不要建 task | 小 bug 可以答**否**直接改 |
| 2 | 让它先定位再改 | 根因定位 | **它说得出为什么会这样**，不是"我改了试试" |
| 3 | 确认根因后再改 | 最小修复 | 改动范围和根因对得上 |
| 4 | — | 验证：原复现路径不再复现 | ★ **你自己复现一遍** |
| 5 | — | 判断要不要记 finding | ★ **拍板点** |

**第 2 步是这个场景唯一容易出事的地方**：AI 很容易跳过定位直接改，改完症状消失但根因还在。

## 我该在哪停下来看

| # | 拍什么 | 为什么 |
|---|---|---|
| 1 | **根因说得通吗** | 症状消失 ≠ 修好了 |
| 2 | 自己复现一遍 | AI 说"已修复"不算数 |
| 3 | 要不要记 finding | 大部分 bug 不需要；暴露了 spec 缺口的需要 |

## 常见卡点

### 「AI 直接开始改代码，没说为什么会这样」

打断，要求先定位。一句话就够：

```
先说清楚根因是什么，我确认后再改。
```

**判据**：它的解释能不能预测这个 bug 在别的什么条件下也会出现？能，说明定位到了；说不出来，那是在试。

### 「修完之后要不要更新 spec」

**默认不要。** 只有当这个 bug 的根因是「spec 没规定这种情况」时才记 finding，而且是记 finding 不是直接改 spec。

判据：**下次别人（或别的 session）遇到同类情况，会不会因为 spec 没写而重犯？** 会，就记 finding。

### 「小 bug 要不要建 Trellis task」

不用。Trellis 自己的规矩就是：一句话能答完、不改文件、不需要调研的，不建 task。

**但如果改动会跨多个文件、或需要先调研**，建 task——你需要那份跨 session 记忆。
