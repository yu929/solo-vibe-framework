# 场景二 · Feat Dev

> 在已有结构上加一个新能力。
>
> **本文件第一版只有骨架**，细节等实跑后补。写在没跑过的时候就是编——那是这套框架要防的事。

## 什么时候用这个场景

**判据**：结构已定（知道有哪些模块、数据怎么组织），这次加的是**新能力**。

和另外两个场景的分界：

| | 走这里 | 走别处 |
|---|---|---|
| 说不出这属于哪个阶段目标 | | [`01-new-product.md`](01-new-product.md)，先写简报 |
| **说得出，是阶段目标下新的一片** | ✅ | |
| 行为不对，不新增能力 | | [`03-fix-bug.md`](03-fix-bug.md) |

**逐片之后这个场景和场景一的差别很小**：都是「从简报切一片 → 进 Trellis」。真正的差别只在**要不要先写简报**——已经有简报了就是这里，还没有就是场景一。

## 和 Fix Bug 的真实分岔

**不是「新功能 vs 修 bug」，是「要不要回写 spec」。**

- **feat 通常要**：新能力常常带来新约定（这类数据怎么存、这种交互怎么表达），那是 `.trellis/spec/` 该长的地方
- **fix 通常不要**：除非它暴露了 spec 的缺口——那走 finding 流程

按这条分岔判，比按"这是功能还是 bug"准得多。

## 开始之前

- [ ] 说得出这次加的能力**属于哪个阶段目标**（说不出 = 该走场景一）
- [ ] 它是**一片**吗——做完之后有一件事是用户能真正做成的？
  - **是** → 继续
  - **不是，它是好几片** → 先回简报 §4 拆开排顺序，一片一片来
  - **不是，它太小了**（一句话能答完、不改文件）→ 直接进 Trellis，不用建 task

## 步骤（骨架）

| # | 我敲什么 | AI 产出 | 怎么确认成了 |
|---|---|---|---|
| 1 | 把这一片加进简报 §4 切片清单 | 更新后的 §4（含依赖） | 能说清它依赖哪几片 |
| 2 | 描述这一片，建 task | Trellis 问要不要建 task → 答**是** | — |
| 3 | 同意进 planning | brainstorm 一问一答 → `prd.md` | 能说清这一片的边界 |
| 4 | 有交互面 → `用 lofi-prototype 出这一片的方案` | 2–3 个方案，只覆盖这一片 | ★ **选案** |
| 5 | — | planning summary，你批准后 `task.py start` | ★ **拍板点** |
| 6 | — | Phase 2 实现 → check | check 通过 |
| 7 | — | Phase 3：**更新 spec** → commit → 归档 | ★ **看它改了哪几条 spec** |

**第 7 步是 feat 和 fix 的分水岭**，也是这个场景唯一需要你多看一眼的地方。

## 我该在哪停下来看

| # | 拍什么 | 为什么 |
|---|---|---|
| 1 | 这真的是**一片**吗 | 不能独立端到端跑通的不是切片，是半截工程 |
| 2 | 选案（有交互面时） | 原型上改是几分钟，实现后是几小时 |
| 3 | planning summary | Trellis 自带的免费闸 |
| 4 | **Phase 3 改了哪几条 spec** | AI 倾向于把一次性决定写成永久约定 |

第 4 条展开：**不是每个新做法都该进 spec**。判据是「下次遇到同类情况，还该这么做吗」——只此一次的，不进。

## 常见卡点

### 「加的能力带出了新屏，要不要回去补 brief」

**只补 §4 切片清单加一行**，写清它依赖哪几片。不用补屏——简报里没有屏清单，屏在这一片自己的 `prd.md` 和原型里。

没有审批要作废，也没有"重新走查"这回事：这一片的原型本来就还没画。

> 旧版这里有一条「结构复用既有方案就可以不重新走查、直接重新拍 `prototype_approved`」的捷径。**那条已删。** 它当时就自带「这是推测」的标注，而且它允许在不更新原型的前提下恢复批准——等于让下游拿着一份不含新屏的旧原型当依据。逐片之后这个问题不存在了：新能力就是下一片，走同一条路。

### 「新屏该长什么样，要不要跟前面的片对齐」

**要，而且这是逐片模式唯一真实的代价。**

`lofi-prototype` 出方案前会先读 `docs/discovery/wireframe/*/final/` 下所有已定稿的屏，同类屏沿用既有模式，偏离要说明理由。但发现不一致的通常是你，不是它——所以你也要知道这条。

### 「简报不存在怎么办」

两种情况：

- **一直没写过**（存量项目）→ 不用为了走流程补一份。直接进 Trellis，结构依据是 `.trellis/spec/` 和已有代码。
- **以为该删所以删了** → 找回来。简报**不是消耗品**（旧版写「首版发布就删」，那是错的）：Trellis 里没有任何一处持有产品全貌，删了这一层就归零。
