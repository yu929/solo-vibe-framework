# 操作手册

> **这是给你自己看的清单，照着做就行。** 不是给 AI 的指令文件。
>
> 日常**直接走 Trellis 的流程**即可（描述需求 → 它带你 Plan → Execute → Finish）。本手册只讲 **Trellis 没有、而这套工作流需要**的那部分。
>
> ⚠️ **首次实跑前**：本手册尚未经过完整实跑。命令名和阶段名来自 Trellis 文档与源码（v0.7.0-beta.3）。第一次跑的时候以实际输出为准，对不上的地方当场改这份手册——**手册的 bug 就是这么修的**。

## 选哪个场景

| 你现在要做的 | 用 | 判据 |
|---|---|---|
| 换机器 / 起新项目 / skill 不触发 | [`00-setup.md`](00-setup.md) | 一次性准备 |
| 从零做一个新东西 | [`01-new-product.md`](01-new-product.md) | 还没有共识的产品结构 |
| 给已有的东西加功能 | [`02-feat-dev.md`](02-feat-dev.md) | 结构已定，加的是新能力 |
| 修一个坏掉的地方 | [`03-fix-bug.md`](03-fix-bug.md) | 行为不符合预期，不新增能力 |
| 停下来看一眼全貌 | [`04-checkpoint.md`](04-checkpoint.md) | 做完 3–5 片 / 阶段目标达成 / 准备发版 |

**边界模糊时按这条判**：

> **这次改动属于哪个阶段目标下的哪一片？**
>
> - 说不出属于哪个阶段目标 → 走「全新产品」，先写简报
> - 说得出，且是新的一片 → 走「Feat Dev」
> - 说得出，且是已有的一片没做对 → 走「Fix Bug」

## Trellis 有什么，这里补什么

**Trellis 有需求收敛**——`trellis-brainstorm` 会一问一答帮你把一个 task 想清楚，而且带一个硬门禁：没有你的显式批准，不许 `task.py start`。这部分很好用，本手册不复述。

**它没有的只有两样，都在 task 之上**：

| 缺什么 | 为什么它没有 | 本手册怎么补 |
|---|---|---|
| **产品全貌** | `.trellis/spec/` 只放编码规范、`prd.md` 只记单次改动、journal 只是时间流水。跑五十个 task 也没有一处回答「这产品现在整体是什么」 | `docs/discovery/brief.md`（六节一页）+ [`04-checkpoint.md`](04-checkpoint.md) |
| **切片顺序** | Trellis 原文：*"Parent/child structure is not a dependency system"* | 简报 §4 切片清单 |

Trellis 自己也是这么设计的——它的 brainstorm 明说 *"Do not invent a project-specific product/spec hierarchy. If the repository already has product docs, use them."* 它**主动**把产品层留空给你。

## 全流程与拍板点

```
                                          ★ = 你必须停下来拍板

  一句话想法
      │
      ├─ 写简报 ──────────────── docs/discovery/brief.md（六节，一页）
      │                                ★ 阶段目标 + 不做清单
      │
      ├─ （可选）探索 ────────── 技术不确定的点，丢弃品验一下
      │
      ├─ 切出第一片 ──────────── 简报 §4 切片清单
      │                                ★ 第一片是哪个
      │
   ═══╪═══════════════ 以下是 Trellis 自己的流程 ═══════════════
      │
      ├─ Phase 1 Plan ────────── brainstorm 一问一答 → prd.md
      │   └─ 有交互面 → lofi-prototype 只画这一片
      │                                ★ 选案
      │      planning summary          ★ 你批准，它才 start
      │
      ├─ Phase 2 Execute ─────── 实现 → check
      ├─ Phase 3 Finish ──────── update-spec → commit → 归档
      │                                ★ 看它改了哪几条 spec
      │
      └─ 下一片（回到「切出下一片」）

  每 3–5 片 / 阶段目标达成 → 04-checkpoint.md
```

**简报是可选的**：不存在时完全不阻塞。小改动就该跳过它直接建 task。

**没有 approved 字段。** 拍板是你读完点头这个动作，不是文件上的标记——没有任何机制读简报的 frontmatter，放个 bool 只会造出一个永远对不上的假状态。这条链上唯一真正的硬门禁是 Trellis 的 planning summary。

## 拍板点清单

| # | 拍什么 | 在哪 | 拍错了的代价 |
|---|---|---|---|
| 1 | **阶段目标 + 明确不做** | 简报 §2 §3 | 最贵。方向错了后面全白做 |
| 2 | **第一片是哪个 / 下一片是哪个** | 简报 §4 | 中等。第一片定下后面都要沿用的结构 |
| 3 | **选哪个方案** | 原型走查 | 原型上改是几分钟，实现后是几小时 |
| 4 | **planning summary** | Trellis，`task.py start` 之前 | 最后一道免费的闸 |
| 5 | **Phase 3 改了哪几条 spec** | Trellis Finish | AI 倾向于把一次性决定写成永久约定 |

**1 和 2 是真正值钱的两个。** 3、4、5 拍错了还能改。

## 一个不在主流程里的出口：`design-review`

上面五个场景**没有一处会自动用到它**，这是设计如此，不是漏了。逐片推进下大部分切片不需要独立的设计准入——Trellis 的 planning summary 门禁就够了。它是**逃生舱**，你主动喊才上场。

你最可能撞上的三种，满足任一条就值得喊一次：

| 什么时候 | 判据 |
|---|---|
| **承重决策刚定稿，准备建第一批 task 之前** | 数据归谁、权限与信任边界画在哪、模块怎么切、哪些是长期契约——这类决定改起来贵，值得在开工前单独审一轮 |
| **你已经陷在"审不完"里出不来** | 症状很好认：换了几个 session / 几个 agent 反复审同一份设计，问题越修越多，每轮都冒出新的，你说不出什么时候算审完 |
| **检查点上发现承重决策中途失效** | 判据是「修它要不要动**已经做完的好几片**」。见 [`04-checkpoint.md`](04-checkpoint.md) 第 4 问 |

第二条是它真正的用途。**它治的不是"审得不够细"，是"停不下来"**——用冻结输入、问题台账、证据门槛、P0–P3 和明确的停止规则强制收敛，最多两轮，然后把反馈渠道转向切片实现和测试（那里的反馈更便宜也更真）。

> **完整清单（含高风险范围变更那一条）在 `design-review` skill 的「什么时候用」**，那里是权威源。这张表只列你日常撞得上的三种。

**怎么喊**：直接说「审一下这个设计能不能开工」「设计审不完了」。

**它不做两件事**：不做需求评审（那是简报和原型走查的事），不做代码评审。编码期发现「这条约定不对」也不走它——那是 4 字段 finding，见下面第四条。

## 四件反复出现的事

不管走哪个场景，这四条都成立。

### 一、每一片都要能独立端到端跑通

判据只有一个：

> **做完这一片，有没有一件事是用户能真正做成的？**

「先把所有表建了」「先搭好框架」不是切片——它们验证不了任何东西，该被**拆进**各自的片里。

### 二、切片不能静默长大

逐片模式最主要的失控形态：每片都"顺手多做一点"，三片之后就回到了一次做全。

发现这一片需要更多东西时，先分清是**本片必需**（少了它主链路就断）还是**顺手想加**。后者记进简报 §4 当后面的片。

### 三、brainstorm 问的每个问题，都是简报里缺的一条

Trellis 的 brainstorm 被合同要求「每条消息只问一个问题」，直到没有你该拍的决策为止。

**答的时候顺手补进简报**，别只在对话里答——对话下个 session 就没了。补完之后下一片会明显变短，因为它的 Evidence Rule 要求「能从仓库文档查到的就别问用户」。

⚠️ 最后半句是推测，实跑后修正。

### 四、编码期发现的东西，先记 finding 再改 spec

AI 在实现或调试时会发现「这个约定其实不对」「这里有坑 spec 没写」。**不要让它直接改 `.trellis/spec/`**——那等于让召回方兼任裁决方，spec 会在几周内被填满未经检验的经验。

四个字段记一条（现象 / 证据 / 该改哪个 spec / 状态），你确认后再让 `trellis-update-spec` 升级。规则见 [`review-adjudication.md`](../specs/universal/guides/review-adjudication.md)。

## 这份手册怎么维护

**照着做的时候，凡是需要停下来问「这步到底该干嘛」的地方，就是手册的 bug。** 当场记进对应文件的「常见卡点」。

各场景的「对 AI 说什么 · 速查」**只写实跑验证过的 prompt**。没跑过的标「实跑后补」，留空不丢人——没跑过就编 prompt，正是这套框架要防的事。
